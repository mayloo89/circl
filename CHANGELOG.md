## [Unreleased]

### Security

- **Auth middleware failed open on NextAuth configuration errors**: `proxy.ts` computed `isLoggedIn` as `!!req.auth`, but NextAuth v5 sets `req.auth` to a truthy *error object* (`{"message":"There was a problem with the server configuration…"}`) instead of `null` when session resolution fails — e.g. `UntrustedHost` on a production build without a trusted host. The truthy error object made every anonymous visitor count as logged in: private routes (`/contacts`, `/chat`, …) returned 200 instead of redirecting to login, and `/login` redirected anonymous visitors away to home. Dev auto-trusts localhost, so only production builds exhibited it; the deployed instance was shielded only by `AUTH_URL` matching the incoming Host. Two-layer fix: the middleware now checks `req.auth?.user` so an unresolvable session **fails closed** (verified: with the config error deliberately reintroduced, private routes still 307 to login), and `trustHost: true` is set in the NextAuth config (safe here — credentials-only auth derives no OAuth callback URLs from the Host header, and the app always sits behind the operator's own reverse proxy). New E2E regression tests pin the wall in both directions: anonymous visitors are redirected from private routes to `/login`, and `/login` itself stays reachable — no such test existed, which is how the bug survived.
- **Dependency vulnerability sweep**: `govulncheck` reported five vulnerabilities reachable from this codebase; all are now cleared. Backend: `jackc/pgx/v5` 5.8.0 → 5.10.0 (GO-2026-5004 — SQL injection via placeholder confusion with dollar-quoted string literals in the driver the whole DB layer runs on), `golang.org/x/image` 0.37.0 → 0.44.0 (GO-2026-5061 / GO-2026-4961 / GO-2026-4962 — panics and excessive memory allocation when decoding malicious WEBP/SFNT input, reachable from the worker's decode of user-uploaded images and the album watermark font rendering), and the `go.mod` Go directive raised 1.25.5 → 1.25.12 so builds require a toolchain containing the `crypto/tls` Encrypted Client Hello privacy-leak fix (GO-2026-5856; the Dockerfile's `golang:1.25-alpine` and CI's `go-version: '1.25'` float to the latest patch). Frontend: `next` 16.2.6 → 16.2.10 plus an in-range minor/patch refresh (`next-intl` 4.13.1, Tailwind 4.3.2, Playwright 1.61.1, MSW 2.15.0, vitest 4.1.10, …), and a new `overrides` entry forces `next`'s vendored `postcss` (pinned at 8.4.31) up to the patched ≥8.5.10 line (GHSA-qx2v-qp2m-jg93 — XSS via unescaped `</style>` in stringify output), taking `npm audit` from 2 moderate findings to 0. `eslint-config-next` is deliberately held at 16.1.1 with `eslint-plugin-react-hooks` pinned at 7.0.1: the 16.2.x config escalates new `react-hooks` rules (`set-state-in-effect`, `static-components`) that flag 29 pre-existing call sites — upgrading the config and fixing those patterns is tracked as a follow-up, separate from this security pass.

### Fixed

- **Chat day separators and expiry countdowns showed English in every locale**: `formatDaySeparator` hardcoded `"en"` (plus literal `"Today"` / `"Yesterday"`), so Spanish and Portuguese users saw English weekday/month names on chat date separators; it now takes the active locale and translated labels. The message expiry badge (`"3h left"`, `"expired"`, `"< 1m"`) was hardcoded too — `formatExpiry` is replaced by `expiryCountdown`, which returns a structured `{unit, value}` that `MessageBubble` renders through new `chatRoom.expiry*` keys. EN/ES/PT.
- **Browse distance labels hardcoded in English**: `"< 1 km away"` / `"N km away"` on browse cards moved to `browse.distanceUnder1Km` / `browse.distanceKmAway` i18n keys. EN/ES/PT.
- **Form inputs didn't announce validation errors to screen readers**: `Input` now sets `aria-invalid` when an error is present and links the error (or helper) text to the field via `aria-describedby`, falling back to a generated id (`React.useId`) when no `id` prop is passed so the label and description associations always hold.

- **DM contact warning shown for every chat, even accepted contacts**: `ChatInput`'s "sharing contact info outside accepted contacts" warning is driven by `room.are_accepted_contacts`, but `GET /chat/rooms` (the endpoint `RoomView` actually loads room state from) never populated that field — only the single-room and create-DM endpoints did — so it was always `undefined`/falsy and the warning rendered in every DM regardless of contact status. `chat.RoomSummary` gained an `are_accepted_contacts` field and `listRoomsHandler` now resolves it per DM room via the same `HandlerConfig.AreContacts` callback the other endpoints already used.
- **Landing page ambient animations ran at full speed under reduced motion**: the global `prefers-reduced-motion` rule in `globals.css` only squashed `animation-duration` to `0.01ms`, which settles one-shot `forwards` reveals on their final frame but does nothing for `infinite`-looping animations — they just kept repeating at the same speed, which visitors with reduced motion enabled saw as the landing's orbit rings, aurora glow, and floating chat bubbles spinning/pulsing very fast instead of being calmed down. Those ambient elements (`components/landing/ConnectionMotif.tsx`) are now tagged with `.landing-orbit-el` / `.landing-aurora-el` / `.landing-float-el` classes and turned off outright (`animation: none !important`) under `prefers-reduced-motion: reduce`.

- **`NEXT_LOCALE` cookie hardening skipped unprefixed routes**: a Wapiti scan flagged the `NEXT_LOCALE` cookie as missing `Secure`/`HttpOnly` on `/es/login`. An earlier fix in `proxy.ts` derived the locale from the request pathname (since next-intl sets the cookie via a raw `Set-Cookie` header rather than the Next.js cookies API, so reading it back never worked), but only matched locale-prefixed paths — the default locale (`es`) uses `localePrefix: "as-needed"` and is reachable unprefixed (`/`, `/login`, etc.), so those responses still carried the un-hardened cookie. `finalize()` now reuses the existing `getLocale()` helper, which falls back to `routing.defaultLocale` when no prefix matches, so the hardened cookie is written on every response regardless of whether the path carries a locale segment.

- **Browse ranking, pause-discovery, and profile-completeness gate**: the browse/explore feed now scores each candidate with a weighted blend of shared interests (35%), activity recency bucketed against a per-session anchor (30%), proximity (25%), and a deterministic per-session shuffle jitter (10%), ordering the results most-relevant-first. The shuffle seed is minted once per browser session (`sessionStorage["browse_seed"]`) and sent as `?seed=` on every request including pagination, so refreshing the page keeps the same order while opening a new tab or session yields a fresh order. A new `discovery_paused` boolean in `profile_preferences` (migration `000046`) lets users hide themselves from browse while still being able to browse others; it is wired through the preferences API and a "Pause discovery" toggle in **Settings → Privacy**. Viewers whose own profile is less than 40% complete see a blurred placeholder grid with a "Complete your profile to unlock browsing" CTA instead of results.

- **Pending-until-approved upload UX**: the frontend now matches the backend's attach-time moderation gate so an image is never sent before it clears review, and the sender always gets clear feedback. `useUpload` no longer fakes an "approved" verdict when the moderation poll times out — it polls for a bounded window (~12s, since the backend can hold an image far longer during a vendor outage) and reports a distinct `pendingReview` state instead of silently sending an image the server would reject. In chat (`RoomView`), the sender sees a local preview of their own image with a "Reviewing image…" shimmer while moderation runs (recipients see nothing until approval), and a dismissible amber "still being reviewed — try again shortly" notice if the hold outlasts the poll window. A `quarantined` verdict is surfaced as a generic rejection, never as a distinct tip-off state. `UploadRejectionModal` gained a non-error "still reviewing" variant, wired into the avatar, onboarding-photo, and album-photo upload flows. New `chatRoom` and `uploadRejection` strings in EN/ES/PT.

- **Image moderation — fail-closed pipeline + attach-time serve-gating**: hardening that makes the moderation pipeline safe for the upcoming CSAM/NCII vendor adapters. Detectors now declare a **severity** (`Moderator.Severity()`): legal-floor detectors are `SeverityHard` and fail *closed* — if the detector errors (e.g. a vendor is unreachable) the upload is held `pending` and retried by asynq with a capped 5-minute backoff over a ~4-hour window, and is never served; the NSFW/heuristic detectors stay `SeveritySoft` and fail open so a flaky classifier can't block uploads. Rejections now carry a **disposition** (`Retain` for admin review / `Purge` / `Quarantine`): a CSAM-class hit is moved to a restricted, never-served `quarantine/` prefix and **preserved**, not deleted, because destroying it can itself be unlawful (migration `000045` adds the `quarantined` status + `moderation_quarantine_key`). Most importantly, uploads are now **gated at attach time on `moderation_status='approved'`** so an un-moderated, rejected, or quarantined image can never reach another user — enforced on chat image attachments (`chat.Service.SaveMessage`), private-album photos (`AddPhoto` plus the serve-time `StreamPhoto` proxy), and avatar / profile-gallery media (resolved URL → storage key via the new `uploads.Store.GetByStorageKey`). A new transient `409 upload_not_approved` (`apierror.CodeUploadNotApproved`) tells the client to wait for approval and retry rather than treat it as a permanent rejection.

- **WebSocket load test**: new `loadtest/ws-load-test.js` (k6) validates the chat hub under many concurrent connections at expected peak. Each virtual user runs the real guest → public-room path (create session → redeem single-use WS ticket → hold a WebSocket open, sending periodically and counting broadcast fan-out), so peak VUs equal peak concurrent connections. Ramping-VUs profile and metric thresholds (handshake p95 < 1.5s, connect/auth error rates, overall checks) make it exit non-zero on regression. Manual/on-demand — not wired into CI. The guest-session per-IP limiter is now env-configurable (`GUEST_IP_RATE`, default 10, `0` disables) so the test isn't throttled when all load comes from one IP. `loadtest/README.md` covers setup, the Grafana signals to watch, and result interpretation.
- **Self-hosted observability stack on the production host (opt-in)**: the full Loki + Alloy + Tempo + Prometheus + Grafana stack is now available in the production compose behind an `observability` compose profile (off by default — it adds ~1 GB RAM, heavy for a small Pi). ### Added

- **In-room moderation for public rooms**: platform admins can kick and mute any participant (guest or registered) from a public room via new admin-only REST endpoints (`POST /chat/rooms/{id}/mod/kick`, `POST /chat/rooms/{id}/mod/mute`, `DELETE /chat/rooms/{id}/mod/mute/{targetID}`). Kick is real-time via a new `kickCmds` channel on the hub — the target receives a `kicked` WS event then their connection is closed; guests are also IP-banned for 24h (SHA-256 hash stored in Redis at `guest:ban:{roomID}:{ipHash}`). Mute durations are admin-chosen (15 min / 1 h / 24 h), stored as Redis keys (`guest:muted:{roomID}:{userID}`) and checked in `readPump` before saving — the sender receives a `you_are_muted` event and the message is dropped. Nicknames containing profanity are blocked at guest-session creation by a new `internal/profanity` package (normalize → deny-list covering the ~50 worst-case slurs in EN/ES/PT, including leet-speak variants); returns `400 CodeProfanityNickname`. `POST /guest/session` now accepts `room_id` and checks for an active IP ban before minting the session (`403 CodeIPBanned`). Frontend: `kicked` / `you_are_muted` WS events handled in `useGuestChat` and `useChat` (expose `isKicked` / `isMuted` state); `PublicRoomShell` renders a full-screen removal modal when kicked and an amber muted banner above the chat input; admin-only `•••` overflow menu per roster participant (Kick, Mute 15 min / 1 h / 24 h) using `useMenuKeyboard` with full ARIA wiring; guest entry gate surfaces localized `ipBanned` and `profanityNickname` errors. All moderation state is Redis-only — no migration needed. New `apierror.CodeIPBanned` + `CodeProfanityNickname`.

- **Anti-bot challenge on guest entry (Cloudflare Turnstile)**: `POST /guest/session` now verifies a Turnstile token server-side before minting a guest session, closing the spam/bot vector on the public, unauthenticated guest surface. New provider-agnostic `internal/captcha` package (Turnstile `siteverify`, 5s timeout) wired into the guest handler via a `Captcha func(ctx, token, ip)` field; the client IP (from `RealIP`) is forwarded for scoring. **Disabled by default** — the check is skipped unless `TURNSTILE_SECRET` is set, so local dev needs no keys. Frontend: a reusable `components/ui/Turnstile.tsx` widget renders on the `/rooms/[roomId]` entry gate (gated on `NEXT_PUBLIC_TURNSTILE_SITE_KEY`, dark theme, auto-loads the script once); the Enter button stays disabled until the challenge is solved, and a 403 surfaces a localized "verification failed" message (EN/ES/PT). CSP (`proxy.ts`) extended to allow `challenges.cloudflare.com` for `script-src`/`frame-src`/`connect-src` (no `unsafe-inline` reintroduced). New `apierror.CodeCaptchaFailed`. Tests: Turnstile verifier (success/failure/empty-token via a stub siteverify server) + guest-handler cases (403 on failure, token forwarded on success).

- **Public rooms with guest-access tier (Phase 1 / MVP)**: admin-created open chat rooms where unregistered guests can enter with a nickname + age-of-majority declaration and start chatting immediately. Guest sessions are ephemeral and Redis-backed (4h TTL, no DB row); guests are text-only, restricted to public rooms only, and rate-limited at 6 messages/minute (configurable via `GUEST_MSG_RATE`). Registered users are visibly marked in the participant list as social proof. Contact-info masking applies unconditionally to guest messages. Service profiles are blocked from posting in public rooms. 24h hard-delete retention for public-room messages (wired into the existing `RetentionCleaner`). Migration `000044` adds the `'public'` room type, the `visibility` column, and indexes, and — because guests have no `users` row — makes `messages.sender_id` nullable and adds a `sender_label TEXT` column for the guest nickname. ### Security

- **Trusted proxy / real IP middleware**: new `middleware.RealIP(cidrs)` + `middleware.ClientIP(r)` extract the real client IP from `X-Forwarded-For` / `X-Real-IP` only when the connection arrives from a configured CIDR (`TRUSTED_PROXIES` env var). When unset (default), `r.RemoteAddr` is used unconditionally, preventing rate-limit bypass via spoofed headers. Wired as the first middleware in the chain.
- **SSE notifications auth switched from JWT-in-URL to single-use tickets**: `GET /notifications/stream` now accepts `?ticket=` instead of `?token=`. Clients call `POST /ws-ticket` (behind RequireAuth) to obtain a 60-second single-use ticket before opening the SSE connection, matching the existing WebSocket auth pattern and preventing access tokens from appearing in server access logs and browser history.
- **Metrics endpoint always requires a token**: `metrics.Handler` now returns 403 when `METRICS_TOKEN` is unset instead of serving Prometheus metrics unauthenticated.
- **bcrypt work factor increased from 10 to 12**: `Register`, `ChangePassword`, and `ResetPassword` all use `bcrypt.DefaultCost+2`, making offline brute-force attacks ~4× harder.
- **Refresh tokens revoked after password reset**: `POST /auth/reset-password` now calls `RevokeAllForUser` on success, closing the gap where an attacker with a stolen refresh token could survive a victim's password reset. `ChangePassword` already had this protection.

- **Atomic rate-limit counters**: Redis `INCR` + `EXPIRE` replaced by a Lua script that sets the TTL only on the first increment, eliminating the race window where a counter could survive indefinitely if the process died between the two commands.
- **Request body size cap**: all JSON API routes are wrapped in a `LimitRequestBody` middleware (1 MiB); file-upload paths apply their own per-category limits and are excluded.

### Security

- **Security hardening — headers, WS origin, CORS, secret scan** ([PR #61](https://github.com/mayloo89/circl/pull/61)):
  - `SecurityHeaders` middleware: `X-Content-Type-Options: nosniff`, `X-Frame-Options: DENY`, `Referrer-Policy: strict-origin-when-cross-origin`, `Cache-Control: no-store` on every response; HSTS (1 year, includeSubDomains) in production only
  - WebSocket `CheckOrigin` replaced `return true` with exact-match check against `CORS_ALLOWED_ORIGINS`
  - `X-Request-ID` added to CORS `ExposedHeaders`
  - `next.config.ts` gains a `headers()` export applying CSP, HSTS, `X-Content-Type-Options`, `X-Frame-Options`, `Referrer-Policy`, and `Permissions-Policy` to all Next.js routes; `script-src` allows `unsafe-eval` in development only
  - Gitleaks secret-scanning job added as the first CI job — blocks the pipeline on real leaked credentials
  - `.gitleaks.toml` allowlist added for the three known test-only secrets in `ci.yml`
- Blocking is strictly caller-scoped (JWT-enforced); no information leak — blocked users' profiles remain accessible, only interaction is suppressed
